SECTION: Related Research Section (2.8)

[Paragraph 329]
ในการพัฒนาระบบยืนยันตัวตนนี้ ได้ทำการศึกษางานวิจัยที่เกี่ยวข้องทั้งในด้านเทคนิคและการนำไปใช้งานจริง ดังนี้

[Paragraph 330]


[Paragraph 331]
2.8.1 Fett, Küsters & Schmitz (2016) — การวิเคราะห์ความปลอดภัย OAuth 2.0 เชิงคณิตศาสตร์

[Paragraph 332]
Fett et al. (2016) ได้ทำการวิเคราะห์ความปลอดภัยเชิงคณิตศาสตร์อย่างเป็นทางการสำหรับ OAuth 2.0 ทั้ง 4 grant types โดยใช้ web attacker model ที่ครอบคลุม ผลการศึกษาพิสูจน์ว่า authorization code flow เมื่อใช้ร่วมกับ HTTPS และการตรวจสอบ state parameter สามารถรับประกันความปลอดภัยด้าน authorization และ session integrity ได้อย่างแข็งแกร่ง นอกจากนี้ยังพิสูจน์ว่า implicit flow มีความปลอดภัยต่ำกว่าเนื่องจาก access token ถูกเปิดเผยใน URL fragment ระบบ TAS ได้นำ authorization code flow มาใช้แต่เพียงอย่างเดียวและเพิ่ม PKCE (S256) เพื่อป้องกัน code interception attacks ตามข้อพิสูจน์ของ Fett et al. [16]

[Paragraph 333]


[Paragraph 334]
2.8.2 Koponen (2016) — การพัฒนา OAuth 2.0 Authorization Server ด้วย Node.js

[Paragraph 335]
Koponen (2016) ได้ออกแบบและพัฒนา OAuth 2.0 authorization server ด้วย Node.js เป็นส่วนหนึ่งของวิทยานิพนธ์ระดับปริญญาโทที่ University of Jyväskylä ประเทศฟินแลนด์ งานวิจัยนี้เสนอว่าการจำกัด grant type ให้ใช้เฉพาะ authorization code การบังคับใช้ authorization code แบบ single-use และการตรวจสอบ redirect URI อย่างเข้มงวด จะช่วยลด attack surface ได้อย่างมีนัยสำคัญ ระบบ TAS มีความสอดคล้องกับแนวทางของ Koponen โดยใช้ Node.js runtime เดียวกัน single-use authorization code pattern เดียวกัน และขยาย model ด้วย PKCE และ Apache Kafka audit logging [17]

[Paragraph 336]


[Paragraph 337]
2.8.3 Philippaerts et al. (2022) — การทดสอบ OAuth 2.0 Compliance ด้วยเครื่องมือ OAuch

[Paragraph 338]
Philippaerts et al. (2022) ได้พัฒนาเครื่องมือ OAuch สำหรับทดสอบความสอดคล้องกับมาตรฐาน OAuth 2.0 และทำการทดสอบ identity providers จริงกว่า 20 รายการกับข้อกำหนดด้านความปลอดภัย 112 รายการ ผลการศึกษาพบว่า providers โดยเฉลี่ยไม่ปฏิบัติตาม 34% ของข้อกำหนด โดยที่พบบ่อยที่สุดคือ PKCE enforcement ที่ขาดหายไป การไม่มี refresh token rotation และ redirect URI validation ที่ไม่เข้มงวด ระบบ TAS ได้รับการออกแบบเพื่อปิดช่องว่างเหล่านี้: บังคับใช้ PKCE S256 เท่านั้น บังคับ refresh token rotation ทุกครั้ง และตรวจสอบ redirect URI แบบ exact matching [18]

[Paragraph 339]


[Paragraph 340]
2.8.4 งานวิจัยด้าน JWT Session Management (2023)

[Paragraph 341]
งานวิจัยที่ตีพิมพ์ในปี 2023 ได้ประเมินความปลอดภัยของ JWT สำหรับ REST API session management โดยวิเคราะห์ signing algorithms และ refresh token rotation patterns ผลการศึกษาแนะนำว่า access token อายุสั้นร่วมกับ one-time-use refresh tokens และ server-side blacklist ให้ความปลอดภัยสูงสุด นอกจากนี้ยังระบุว่าการ logout ต้องทำการ blacklist ทั้ง access token และ refresh token พร้อมกัน ระบบ TAS ปฏิบัติตามคำแนะนำทั้งหมด: access token 1 ชั่วโมง, refresh token rotation แบบ one-use และ MongoDB TokenBlacklist ที่ revoke ทั้งสอง token เมื่อ logout [19]

[Paragraph 342]


[Paragraph 343]
2.8.5 Melton et al. (2017) — การ Deploy ระบบ Single Sign-On ในสถานพยาบาล

[Paragraph 344]
Melton et al. (2017) ได้บันทึกการ deploy ระบบ Single Sign-On ในระบบโรงพยาบาล 6 แห่งที่ต้องการ password มากกว่า 12 รายการต่อคน การศึกษาวัดผลลัพธ์ที่เป็นรูปธรรม พบว่า SSO ช่วยลดเวลาที่ใช้ในการยืนยันตัวตน 9.51 นาทีต่อคนต่อวัน คิดเป็นมูลค่า 92,146 ดอลลาร์สหรัฐต่อสถานพยาบาลต่อปี นอกจากนี้ระบบ centralized authentication ยังช่วยรวม audit logs ไว้ในที่เดียว กรณีศึกษานี้ยืนยันว่าการเลือกสถาปัตยกรรมแบบ centralized authentication ซึ่งเป็นแนวทางเดียวกับที่ระบบ TAS ใช้ ให้ผลประโยชน์ด้านความปลอดภัยและประสิทธิภาพที่วัดได้จริงในองค์กร [20]

[Paragraph 1116]
ใช้ bcrypt ด้วย salt rounds 10 รอบในการเข้ารหัสรหัสผ่าน

[Paragraph 1117]


[Paragraph 1118]
3.8.5 Refresh Token Rotation

[Paragraph 1119]
ทุกครั้งที่มีการใช้ refresh token จะสร้าง refresh token ใหม่ และ blacklist token เก่าทันที (ทั้ง Auth path และ OAuth session path)

[Paragraph 1120]
- Old refresh token ถูก blacklist ก่อนที่จะออก token ใหม่ (ป้องกัน race condition)

[Paragraph 1121]
- TokenBlacklist ใช้ upsert ป้องกัน duplicate key crash (E11000 safe)

[Paragraph 1122]
- เมื่อ logout: blacklist ทั้ง access token และ refresh token พร้อมกัน

[Paragraph 1123]
- เมื่อ reset password: revoke ทุก session และ blacklist refresh tokens ทั้งหมด

[Paragraph 1124]
- PKCE: รองรับเฉพาะ S256 method เท่านั้น (plain method ถูกปฏิเสธ)

[Paragraph 1125]
- Authorization code: atomic exchange ด้วย findOneAndUpdate ป้องกัน replay race condition

[Paragraph 1126]


[Paragraph 1127]
3.8.6 Token Blacklisting

[Paragraph 1128]
เมื่อ user logout หรือ revoke token จะถูกเพิ่มเข้า blacklist

[Paragraph 1129]
จนกว่า token จะหมดอายุ

[Paragraph 1130]

3.8.9 Token Blacklist Middleware Check

[Paragraph 1141]
ทุก request ผ่าน authenticate middleware จะตรวจสอบ token กับ TokenBlacklist ก่อน JWT verify

[Paragraph 1142]
- ทำให้ invalidate access token ได้ทันทีโดยไม่รอหมดอายุ

[Paragraph 1143]
- ใช้สำหรับ: logout, emergency lockdown, OAuth token revoke

[Paragraph 1144]
- TokenBlacklist.isBlacklisted(token) เรียกก่อน jwt.verify()

[Paragraph 1145]
- tokens ที่ถูก revoke จะถูก reject ทันที

[Paragraph 1146]

[Paragraph 1150]
